# Found practices

Lessons from shipping iPhone apps, games, and websites with coding agents in 2026. Each entry is something that happened in a real project and the rule it produced. The rules are already wired into `SKILL.md` and `standard.md`; this file holds the reasons, and is the briefing to hand delegates.

| ID | What happened | Rule |
|---|---|---|
| FP-1 | A game's first build passed 339 tests and 1,000 bot matches. On the simulator it showed static tokens, synthesized beeps, no visible fight, and an instant loss for a new player. | Green tests are not the bar. Name the reference products at kickoff and score the experience a new user gets (UX-5, CS-1, GM-1..3). |
| FP-2 | An iPhone-only app was rejected under App Review Guideline 4: its first-launch dialog was clipped on an iPad Pro 11-inch, where Apple reviews iPhone apps in compatibility mode. Only iPhone sizes had been checked. | iPad compatibility mode is in every evidence set for iPhone apps (F-6). |
| FP-3 | A release retrospective traced a recurring resume bug (characters and health bars hidden after Continue) to UI tests that were not in the default test runner. | The default test command runs every suite, before every push (EN-1). |
| FP-4 | Test fixtures visible to the game engine caused a class-name collision in the exported build that could stop matches from starting on a real device. | Verify the shipped artifact, not only the editor (EN-2, step 1). |
| FP-5 | Later sessions re-ran reviews that had already passed, because completion was never written down. | Bind every receipt to a build or source hash in the ledger; skip a check only while the hash still matches (step 1, step 8). |
| FP-6 | The owner asked to "check the apps" and got functional QA. They had already verified function themselves and wanted design quality. | Confirm the dimensions in scope before a run; the override can drop a dimension the owner covers (step 0). |
| FP-7 | Builds the building agent had called ready were rejected on first look by the owner (FP-1) and by App Review (FP-2). | A self-score never closes a gate. A separate judge sees receipts only and re-checks last round's findings (step 4, step 6). |
| FP-8 | Delegates start from a clean context and see only the skills named in their prompt. The owner asked that the design skills be passed to every implementer and reviewer. | Name `impeccable`, `mobile-ui-ux`, and this skill in every delegate prompt. |
| FP-9 | Unattended loops lose in-context counters on compaction, then redo finished work or grind one failure. | Keep the round counter in the ledger, cap rounds, and escalate with receipts at the cap (step 7). |
| FP-10 | Game audio was checked by file integrity and signal analysis because nobody could listen to it; the report said so. | Say what was and was not checked. A gap is reported as a gap (step 2). |
| FP-11 | A save after elimination wrote an empty game state, and the lobby then offered a broken Continue. | Test save → kill → resume at every persisted phase, including terminal ones (FN-2). Writes are atomic with a valid backup (FN-4). |
| FP-12 | A test assumed result text could never overlap a stage transition. A timer-ending fight made that valid, so the test was narrowed for that case only, game code unchanged, reason recorded. | Diagnose a failing check at its layer. Change a test only when the spec says the new behavior is correct, and record why (step 5, F-10). |
| FP-13 | QA runs left simulator clones and dev servers running and ate RAM on the owner's machine. | Close by stopping and deleting what the run created; leave the owner's devices alone (step 8). |
| FP-14 | The owner asked that researched best practices enter the shared workflow only after they confirm them. | Project-wide rule changes go to the owner first; the ledger records who confirmed each one. |
| FP-15 | After the iPad rejection, the plan resubmitted the iPhone-only build with the clipping fixed and handed native iPad layout off as separate work. | When the round cap or a deadline hits, ship the fix that clears the floor and record the deferred work with its trigger. |
| FP-16 | This skill's first draft was handed to a fresh agent with only a deployed web app and no owner. It found real defects (320 px overflow, 2.56:1 contrast, an edit lost on immediate reload) and returned 32 places where the wording made it guess: audit mode had no close step, gap and fail were conflated, n/a had no rule, placeholders in the template read as defaults. | Forward-test a skill on a real target with a fresh agent before publishing, and ask for the friction list, not only the result. Define every outcome word (pass, fail, gap, n/a) and give every fallback a scoring rule. |
